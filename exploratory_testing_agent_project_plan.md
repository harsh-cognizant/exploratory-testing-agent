## 1. Executive Summary

Modern software teams rely on scripted test suites that can only catch bugs they already imagined. As AI-generated code accelerates development velocity, the gap between what is written and what is tested widens every sprint. The **Exploratory Testing & Coverage Gap Discovery Agent** is an AI-powered system that autonomously navigates a web application, thinks like a senior QA engineer, discovers unknown risks, learns from every run, and generates ready-to-use test cases for every gap it finds.

Unlike existing tools that execute predefined scripts faster, this agent operates without a script. It builds a live coverage intelligence graph of the application, prioritises unexplored areas by risk, simulates multiple human-like user personas, remembers what it found across runs, and continuously improves its exploration strategy. The result is a QA system that finds what humans forgot to test — before users do.

**Core innovation:** The agent applies goal-oriented, risk-weighted, memory-augmented exploration to discover the unknown unknowns in any web application's test coverage.

## 2. Problem Statement

### 2.1 The Known-Unknown Gap

Scripted test suites are inherently limited to scenarios that a human tester explicitly imagined and wrote down. Every test suite, regardless of coverage percentage, has a blind spot: the scenarios nobody thought of. These are the exact conditions under which production bugs occur.

In a typical enterprise team:
- 60–70% of QA engineering time is spent maintaining existing tests, not discovering new gaps
- Code coverage metrics measure line execution, not scenario completeness
- A suite can report 85% coverage while missing entire user journeys entirely

### 2.2 AI-Generated Code Acceleration

Over 40% of code written in 2025 was generated by AI tools such as GitHub Copilot and Cursor. AI writes code faster than humans write tests for it. There is currently no AI-native quality layer that acts as a counterpart to AI-generated code — the agent fills this gap directly.

### 2.3 Accessibility and Compliance Blind Spots

Over 5,000 digital accessibility lawsuits were filed in the US in 2025, a 20% increase year-on-year. Accessibility issues are almost never caught by standard scripted tests because they require contextual, cross-element reasoning that rule-based automation cannot perform.

### 2.4 Multi-Framework Fragmentation

74.6% of teams run two or more automation frameworks simultaneously. Coverage data is siloed across tools, making it impossible to get a unified view of what is and is not tested. No single tool aggregates and visualises cross-framework gaps.

### 2.5 Problem Summary Table

| Problem | Current Reality | Impact |
|---|---|---|
| Scripted tests miss unknown risks | Tests only cover what testers imagined | Production bugs from unconsidered scenarios |
| AI code ships without AI-quality layer | Copilot writes code, nobody tests the edge cases | Silent regressions in AI-generated code |
| Coverage metrics mislead teams | Line coverage ≠ scenario coverage | False confidence before releases |
| Test maintenance consumes 60–70% of QA time | Engineers fix broken tests instead of finding new gaps | Shrinking coverage over time |
| Accessibility gaps go undetected | Rule-based tools miss contextual accessibility issues | Legal exposure and user exclusion |

## 3. Proposed Solution

### 3.1 Solution Overview

The agent is a five-layer autonomous system that:

1. **Maps** the application's complete testable surface as a live graph
2. **Prioritises** unexplored areas by risk score before exploring them
3. **Explores** the application using multiple simulated human personas
4. **Remembers** findings across runs and improves strategy over time
5. **Generates** ready-to-use test cases for every gap it discovers

### 3.2 Key Differentiators

**Goal-oriented, not script-oriented.** The agent is given an objective ("find all failure paths in checkout") and reasons about how to achieve it, rather than executing predefined steps.

**Risk-weighted priority.** It does not explore randomly. Areas with recent code changes, historical defects, or high business criticality are explored first.

**Behavioural simulation.** The agent does not behave like a robot. It simulates a confused user, a power user, and a malicious user — each uncovering different classes of defects.

**Continuous learning.** Every run makes the next run smarter. The agent remembers what it found, skips already-validated paths, and elevates risk scores for historically problematic areas.

**Automated test output.** Every gap discovered is automatically converted into a runnable Pytest test case, closing the loop from discovery to prevention.

### 3.3 What the Agent Is Not

- It is not a replacement for scripted regression suites — it complements them
- It is not a security penetration testing tool — it surface-tests, not deep-probes
- It is not a performance testing tool — it tests functional and UX correctness, not load

## 5. Five Core Layers — Detailed Design

### 5.1 Layer 1: Coverage Intelligence Graph

#### Purpose
Build a live, queryable knowledge graph of every testable surface in the application — pages, routes, API endpoints, UI states, and user flows — and overlay it with existing test coverage to expose gaps as graph nodes.

#### How It Works

**Step 1 — Route Discovery**  
The crawler visits the application URL and recursively discovers all reachable pages, form elements, buttons, API calls, and state transitions. It uses Playwright to render JavaScript-heavy SPAs correctly.

**Step 2 — Graph Construction**  
Each discovered element becomes a node. Navigation paths, form submissions, and API calls become directed edges. The graph is built using NetworkX in-memory and optionally persisted to a lightweight graph store.

**Step 3 — Coverage Overlay**  
Existing test files (Playwright scripts, Pytest files, or a mock JSON) are parsed to identify which nodes are already exercised. Covered nodes are marked green. Uncovered nodes are marked as gaps.

**Step 4 — Gap Detection**  
The Claude API analyses the uncovered nodes and reasons about which ones represent meaningful test gaps versus dead code. This prevents the agent from chasing untestable paths.

#### Node Schema

```json
{
  "id": "node_checkout_payment_form",
  "type": "form",
  "url": "/checkout",
  "element": "payment_form",
  "covered": false,
  "risk_score": 0.87,
  "last_changed": "2026-05-01",
  "defect_count_historical": 3,
  "business_criticality": "high",
  "gap_reason": "Payment form has no negative path coverage"
}
```

#### Edge Schema

```json
{
  "source": "node_cart",
  "target": "node_checkout_payment_form",
  "type": "navigation",
  "transition": "click_proceed_to_checkout"
}
```

### 5.2 Layer 2: Risk Prioritisation Engine

#### Purpose
Rank every coverage gap by the probability and severity of a defect being present, so that exploration time is always spent on the highest-value targets first.

#### Risk Scoring Formula

```
risk_score = (w1 × change_frequency) + (w2 × defect_density) + (w3 × criticality)

where:
  w1 = 0.35  (recent changes are the strongest predictor of new bugs)
  w2 = 0.40  (historical defect areas break again most often)
  w3 = 0.25  (business impact multiplier)

  change_frequency  = commits_last_30_days / max_commits (normalised 0–1)
  defect_density    = defects_last_6_months / total_defects (normalised 0–1)
  criticality       = { auth: 1.0, payment: 1.0, data: 0.9, navigation: 0.5, ui: 0.3 }
```

#### Risk Bands

| Score | Band | Colour | Action |
|---|---|---|---|
| 0.8 – 1.0 | Critical | Red | Explore immediately, every persona |
| 0.6 – 0.79 | High | Amber | Explore in first pass |
| 0.4 – 0.59 | Medium | Yellow | Explore in second pass |
| 0.0 – 0.39 | Low | Green | Explore only if time permits |

#### Exploration Queue Output

```json
{
  "queue": [
    { "node_id": "node_checkout_payment_form", "risk_score": 0.91, "reason": "High defect history + recent change + payment flow" },
    { "node_id": "node_login_error_state", "risk_score": 0.84, "reason": "Auth flow, no negative path coverage" },
    { "node_id": "node_cart_quantity_update", "risk_score": 0.72, "reason": "Recently modified, no boundary value tests" }
  ]
}
```

### 5.3 Layer 3: Behavioural Exploration Engine

#### Purpose
Simulate how real humans (including confused, impatient, or malicious ones) actually use the application — uncovering defects that only emerge from realistic, unpredictable interaction patterns.

#### Personas

**Persona 1: Confused User**
- Fills forms with incorrect data types (text in number fields, numbers in email fields)
- Submits forms with required fields empty
- Navigates backwards mid-flow (back button during checkout)
- Refreshes the page mid-transaction
- Double-clicks submit buttons
- Tries to access pages out of sequence (goes to /checkout without items in cart)

**Persona 2: Power User**
- Uses keyboard shortcuts for everything
- Rapid successive clicks on interactive elements
- Opens the same page in multiple tabs simultaneously
- Completes flows in minimum possible clicks, skipping optional steps
- Uses browser autofill with unexpected data formats

**Persona 3: Malicious User**
- Enters SQL-injection-style strings in all text fields: `'; DROP TABLE users; --`
- Enters XSS payloads in name/comment fields: `<script>alert(1)</script>`
- Enters extremely long strings (500+ characters) in all inputs
- Manipulates URL parameters directly: `/product?id=-1`, `/cart?qty=999999`
- Attempts to access authenticated routes without logging in

#### Anomaly Detection

The engine captures the following anomaly types during exploration:

| Anomaly Type | Detection Method | Severity |
|---|---|---|
| JavaScript console error | Playwright console listener | Medium |
| HTTP 4xx / 5xx response | Playwright network listener | High |
| Unexpected redirect | URL change monitoring | Medium |
| UI element disappears unexpectedly | DOM mutation observer | Medium |
| Form accepts invalid data without error | Response validation | High |
| Page crashes / blank render | Error boundary detection | Critical |
| Broken layout on edge-case input | Screenshot diff | Low |

#### Finding Object Schema

```json
{
  "id": "finding_001",
  "timestamp": "2026-05-12T10:23:11Z",
  "persona": "confused_user",
  "page": "/checkout",
  "node_id": "node_checkout_payment_form",
  "action": "Submitted payment form with empty card number",
  "anomaly": "Form submitted successfully, no validation error shown",
  "anomaly_type": "form_accepts_invalid_data",
  "severity": "high",
  "screenshot_path": "screenshots/finding_001.png",
  "reproduction_steps": [
    "Navigate to /cart with at least one item",
    "Click Proceed to Checkout",
    "Leave card number field empty",
    "Click Pay Now"
  ],
  "suggested_assertion": "Assert that payment form rejects empty card number with visible error"
}
```

### 5.4 Layer 4: Memory & Continuous Learning Loop

#### Purpose
Build a persistent, cross-run memory so that the agent becomes smarter with every scan — skipping already-validated paths, elevating recurring risk areas, and adapting its exploration strategy based on historical patterns.

#### How Memory Works

**Storage:** ChromaDB (local vector database) with `sentence-transformers` embeddings.

**On each finding:** The finding description, page context, and anomaly type are embedded and stored as a vector with metadata.

**On next run start:** Before exploring a node, the agent queries ChromaDB for semantically similar past findings on that node. If a match is found with cosine similarity > 0.85:
- If the past finding was resolved (fix confirmed): mark as low priority
- If the past finding was not resolved: elevate risk score by 0.15
- If a similar finding exists on a different page: flag as pattern, explore all similar pages

**Risk score update after each run:**
```python
def update_risk_score(node_id, findings_this_run):
    base_score = graph.nodes[node_id]['risk_score']
    if len(findings_this_run) > 0:
        # Bug found — increase risk for next run
        new_score = min(1.0, base_score + 0.15 * len(findings_this_run))
    else:
        # No bugs found — slightly decrease risk
        new_score = max(0.0, base_score - 0.05)
    graph.nodes[node_id]['risk_score'] = new_score
```

**Run comparison:** Each run is stored with a timestamp and summary. The dashboard can overlay two runs to show which nodes changed risk level, which gaps were closed, and which new gaps appeared.

#### Memory Entry Schema

```json
{
  "id": "mem_finding_001",
  "run_id": "run_20260512_1023",
  "node_id": "node_checkout_payment_form",
  "embedding": "[vector...]",
  "metadata": {
    "severity": "high",
    "persona": "confused_user",
    "anomaly_type": "form_accepts_invalid_data",
    "resolved": false,
    "run_date": "2026-05-12"
  }
}
```

### 5.5 Layer 5: Output & Test Generation

#### Purpose
Convert every discovered gap into a structured, actionable output — a severity-ranked gap report and a set of runnable Pytest test cases that can be committed directly to the test suite.

#### Gap Report Structure

```json
{
  "report_id": "report_20260512_1023",
  "generated_at": "2026-05-12T10:45:00Z",
  "app_url": "http://localhost:3001",
  "summary": {
    "total_nodes_discovered": 47,
    "nodes_covered_before": 21,
    "coverage_before_percent": 44.7,
    "gaps_found": 12,
    "critical_findings": 3,
    "high_findings": 5,
    "medium_findings": 4,
    "estimated_coverage_after_percent": 71.3
  },
  "top_risks": [...],
  "findings": [...],
  "generated_tests": [...]
}
```

#### Pytest Generation

The agent uses Claude to generate a complete Pytest test function for each high or critical finding.

**Prompt input to Claude:**
```
Finding: Submitted payment form with empty card number.
Anomaly: Form submitted successfully without validation error.
Page: /checkout
Reproduction steps: [...]

Generate a Pytest test function using Playwright fixtures that:
1. Sets up the required precondition (cart with items)
2. Performs the exact action that triggered the anomaly
3. Asserts the correct expected behaviour
4. Includes a docstring explaining what is being tested and why
```

**Example generated output:**
```python
def test_checkout_payment_form_rejects_empty_card_number(page):
    """
    Verifies that the payment form on /checkout shows a validation
    error when the card number field is submitted empty.
    Discovered by: Confused User persona, Run 2026-05-12
    Risk level: High
    """
    # Precondition: add item to cart
    page.goto("http://localhost:3001/products")
    page.click("[data-testid='add-to-cart-btn']")
    page.goto("http://localhost:3001/checkout")

    # Action: submit payment form with empty card number
    page.fill("[data-testid='card-number']", "")
    page.click("[data-testid='pay-now-btn']")

    # Assertion: validation error must be visible
    assert page.locator("[data-testid='card-error-msg']").is_visible(), \
        "Expected validation error for empty card number, none shown"
```

### 11.2 Claude API Integration

```python
import anthropic
import json
import os

client = anthropic.Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))

def analyse_gaps(routes: list, existing_coverage: list) -> list:
    """Ask Claude to identify meaningful coverage gaps from route list."""
    
    prompt = f"""
You are a senior QA engineer analysing an application's test coverage.

Application routes discovered: {json.dumps(routes, indent=2)}
Currently covered by tests: {json.dumps(existing_coverage, indent=2)}

Identify the top coverage gaps. For each gap, return a JSON array where each item has:
- node_id: string identifier
- page: the URL path
- gap_reason: one sentence explaining why this is a meaningful gap
- risk_factors: list of risk factors present

Return ONLY valid JSON, no explanation.
"""
    
    message = client.messages.create(
        model="claude-sonnet-4-20250514",
        max_tokens=1000,
        messages=[{"role": "user", "content": prompt}]
    )
    
    return json.loads(message.content[0].text)
```

### 11.3 ChromaDB Memory Integration

```python
import chromadb
from sentence_transformers import SentenceTransformer

class AgentMemory:
    def __init__(self):
        # Use PersistentClient (chromadb >= 0.5.x API) so memory survives process restarts
        self.client = chromadb.PersistentClient(path="./chroma_store")
        self.collection = self.client.get_or_create_collection("findings")
        self.model = SentenceTransformer('all-MiniLM-L6-v2')
    
    def store_finding(self, finding: dict):
        text = f"{finding['page']} {finding['anomaly']} {finding['persona']}"
        embedding = self.model.encode(text).tolist()
        self.collection.add(
            ids=[finding['id']],
            embeddings=[embedding],
            metadatas=[{
                "node_id": finding['node_id'],
                "severity": finding['severity'],
                "resolved": False
            }]
        )
    
    def query_similar(self, node_id: str, context: str, top_k: int = 3):
        embedding = self.model.encode(context).tolist()
        results = self.collection.query(
            query_embeddings=[embedding],
            n_results=top_k,
            where={"node_id": node_id}
        )
        return results
```
